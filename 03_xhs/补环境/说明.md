# 小红书 x-s 补环境说明

这份文档记录：**如何一步步探测并补出一套能在纯 Node 里跑起来的小红书签名环境**，以及过程中踩到的坑。

最终结果：`window.mnsv2`（x-s 的核心，由 vmp.js 虚拟机提供）可以在纯 Node 下正常调用，签名完全离线生成，不再需要浏览器参与。

---

## 一、目录与用法

```
03_xhs/
├── CDP/
│   └── sign.py            # 另一条路线：借真实 Chrome 的页面算签名（保留，可用）
└── 补环境/
    ├── env.js             # ★ 补出来的浏览器环境（本文的主角）
    ├── vmp.js             # 目标：小红书的虚拟机脚本（288KB 单行混淆）
    ├── sign_node.js       # ★ 纯 Node 出签：node sign_node.js <path> <bodyJson>
    ├── fetch_feed_node.js # ★★ 纯 Node 端到端取数（补环境出签 + Rust 引擎传输）
    ├── xs_common.js       # ★ 离线复刻的 xsCommon（X-S-Common 也在 Node 里算）
    ├── fetch_feed.py      # 备选：Python 版取数（curl_cffi + 浏览器兜底）
    ├── creds.json         # 凭证缓存：cookies + X-S-Common + 设备信息
    ├── code.js            # 原始调用样本（保留）
    └── 1.html             # 浏览器复盘用页面
```

用法：

```bash
# ★ 纯 Node 端到端取数（推荐）：不出 Node、不开浏览器、不用 Python
cd 03_xhs/补环境
node fetch_feed_node.js                 # 默认 chrome_149 档案
node fetch_feed_node.js --profile chrome_149

# 只要签名（纯 Node）
node sign_node.js "/api/sns/web/v1/homefeed" '{"cursor_score":"","num":20}'
# => {"X-s":"XYS_...","X-t":"...","X-S-Common":"...","x3":"mns0101_...","x5":"<md5>"}

# 备选：Python 版（外部 curl_cffi 被拒时自动用浏览器上下文兜底）
uv run python 03_xhs/补环境/fetch_feed.py [--refresh] [--direct]
```

> 依赖：`npm install @zionsssx/freq-js`（Rust 引擎 wreq 的 Node 绑定，
> 同时仿 Chrome 的 **JA3 + Akamai HTTP/2** 指纹；macOS/Linux 有预编译）。
> Node 自带的 `fetch`/`undici` 指纹不是 Chrome，直连会被 461。

## 二、x-s 的结构（逆向自线上 vendor-dynamic）

拦截器真正使用的是 `seccore_signv2`：

```js
function seccore_signv2(url, data) {
    var c = url + (data 是对象/数组 ? JSON.stringify(data) : (typeof data === "string" ? data : ""));
    var u = ed.Pu(c);                                // md5(url + body)  -> x5
    var p = ed.Pu(url);                              // md5(url)
    var v = window.mnsv2(c, u, p);                   // ★ 虚拟机算的 x3
    var S = { x0: w.i8, x1: "xhs-pc-web", x2: window[w.mj] || "PC",
              x3: v, x4: data ? typeOf(data) : "", x5: u };
    var R = buildEncSskSign(u);                      // 依赖 localStorage 的 ssk，未登录时 undefined
    if (R) { S.x6 = R.encSskSign; S.x7 = R.encSsk; }
    return "XYS_" + ed.xE(ed.lz(JSON.stringify(S))); // 自定义 base64(utf8(JSON))
}
```

配套 helper（线上 webpack 模块 384 的导出）：

```js
r.d(a, { Pu: md5, kn: crc32, lz: encodeUtf8, tb: w, xE: b64Encode })
// 自定义 base64 字母表（不是标准表）：
// ZmserbBoHQtNP+wOcza/LpngG8yJq42KWYj0DSfdikx3VT16IlUAFM97hECvuRX5
```

实测取到的常量：`x0 = "4.4.3"`（SDK 版本）、`x2 = "Mac OS"`（平台）。

另一个请求头 `X-S-Common` 由 `xsCommon` 生成，结构是一串设备指纹：

```json
{"s0":3,"s1":"","x0":"1","x1":"4.4.3","x2":"Mac OS","x3":"xhs-pc-web","x4":"6.56.2",
 "x5":"<某个 cookie>","x6":"","x7":"","x8":"<localStorage 里的 mini UA>","x9":<hash>,
 "x10":<计数>,"x11":"normal","x12":"<时间戳>;<时间戳>"}
```

## 三、探测与补环境的过程（重点）

方法固定为三步循环，和 `02_a_bogus/toutiao` 那套一样：

> **看现象（代理日志 / 报错） → 判断缺什么 → 补 → 再跑**

### 阶段 0：起点——一个"什么都不缺"的假象

`node code.js` 报 `TypeError: window.mnsv2 is not a function`。

`env.js` 自带 get/set 代理日志，看上去虚拟机一路正常：读完 `WebAssembly`、`Object`、`document.addEventListener`、`localStorage.getItem`、`location.host`、`document.cookie`、`document.body`、`insight`、`xhsFingerprintV3` 之后**静默结束**，一个异常都没有。

> **坑点一：不要相信"没有异常"。** 后来才知道它把异常吞了（见阶段 5）。

### 阶段 1：先确认浏览器里到底需要什么

用一个**对照实验**：伪造 `www.xiaohongshu.com` 源，页面里只放 `vmp.js`，看它创建了哪些全局。

发现两个基本事实：

1. `<script>` 放 `<head>` 里会炸：`TypeError: Cannot read properties of null (reading 'removeChild')` —— 脚本执行时 `document.body` 还是 `null`，而虚拟机初始化第一步就要操作 DOM。**挪到 `<body>` 里就能定义出 `window.mnsv2`**。
2. 成功时浏览器里 `window.mnsv2` 是 `function`，而 `xhsFingerprintV3`、`insight` **同样是 undefined**。

> **坑点二：别把"线上页面存在的东西"当成必要条件。** 我曾错误地把 `insight`、`xhsFingerprintV3` 当成缺失项去补，反而把分支带偏。

### 阶段 2：用 `new Function` 钩子看到动态检测

虚拟机会用 `new Function` 编译几段检测代码，钩住 `Function` 构造函数就能看到原文：

| 编译的代码 | 含义 |
|---|---|
| `try{var _ceh = 1;eval("_ceh;window")}catch(e){return true;} return false;` | 检测 `eval` 是否被劫持 |
| 16972 字符的内嵌 JS | 指纹采集（localStorage / performance / DOM 遍历） |
| `let e=document.getElementsByTagName("*"),t=new Set;for(let a of e)t.add(a.tagName.toLowerCase());return t` | **枚举文档里的所有标签名**，空集合就判定"不是浏览器" |

对应补法：给出真实 DOM 树（`html > head/body > meta/title/link/div/script`），并让 `getElementsByTagName` 真正遍历子树。

### 阶段 3：原生性与形态检测

| 现象 | 判断 | 补法 |
|---|---|---|
| `Function.prototype.toString` 命中 Node 的 `Navigator.prototype.platform` | 原生性检测 | 把 `Navigator.prototype` 上的 getter 用 `Proxy` 包一层（V8 对 Proxy 函数做 toString 会返回 `[native code]`） |
| 只包 `navigator` 的子对象，浏览器里虚拟机立刻退出（轨迹长度 0） | **它早期就在查这些全局的属性描述符** | 把 `document/navigator/location/screen/history/localStorage/...` 从数据属性改成 **accessor**（真机就是这样） |
| `get document.all` | 真机 `typeof document.all === 'undefined'` 且对象存在（`[[IsHTMLDDA]]`），给成 `[]` 等于自报家门 | 复用 `02_a_bogus/toutiao/document_all.node`（C++ 里 `MarkAsUndetectable()`）造出真正的 `document.all` |
| 原型伪造检测 | `[object Navigator]`、`[object HTMLDocument]`、`[object Location]`、`[object History]`、`[object Storage]` | 逐个 `Object.defineProperty(obj, Symbol.toStringTag, ...)` |
| `[native code]` 篡改检测 | SDK 用 `fn.toString().indexOf('[native code]')` 判断是否被 hook | 移植 `markNative` + `Function.prototype.toString` WeakSet 白名单 |

Node 环境特征另外两条：把 `process` 藏掉；vmp.js 放到**裸函数作用域**（`new Function(src)()`）里跑，这样 `require / module / exports / __dirname` 都不在它的作用域里。

### 阶段 4：走到了 wasm 与"最后一层"

用 `WebAssembly.instantiate` 钩子确认：虚拟机会实例化一个 36414 字节的 wasm（导出 `xy_<md5>` 之类的混淆函数），并且在 Node 里**实例化成功**。但 `mnsv2` 仍不出现。

期间还验证过：内存探针显示调用 `mnsv2` 前后 wasm 共享内存**零字节变化**——所以 mnsv2 不是那个 wasm 实现的，wasm 是别的用途。

### 阶段 5：真凶——一个被静默吞掉的 TypeError

最后定位靠的是两条线索：

1. DOM 探针显示，虚拟机拿**垃圾参数**调用 DOM 方法：`document.body.removeChild(undefined)`、`removeChild(window)`。
2. 我们的实现里有一句 `child.parentNode = null`，遇到 `undefined` 会抛 `TypeError`；而这个异常**被虚拟机字节码层的 try/catch 吞掉**，于是它"悄无声息地跳过"了定义 `mnsv2` 的那一步。

补法（**决定性的一行**）：

```js
appendChild: function (child) {
    if (child === null || typeof child !== 'object') return child   // 容错，绝不抛错
    ...
}
```

改完立刻：

```
>>> mnsv2: function
```

> **坑点三（最重要）：补环境时所有对象的方法都必须对垃圾参数容错。**
> 一旦抛异常被虚拟机吞掉，现象就是"所有检测都通过、槽位一个不少、零异常，但结果就是缺失"，非常难查。

### 阶段 6：出签与传输

- 用 `crypto` 复刻 `md5`，实现自定义字母表的 base64，按 `seccore_signv2` 拼出 `X-s`。
- 实测两边前缀逐字符一致：`XYS_2UQhPsHCH0c1+shAHjIj2erjwjQhyoPTqBPT49pjHjIj2eHjwjQ+GnPW/MPjNsQhPUHCHfM1qAZlPebK...`
- **`X-S-Common` 必须原样使用**：第一次我顺手把里面的 `x10` / `x12` 改成当前时间戳 → 461；改回捕获的原值 → 200。
- **传输层有两个硬要求**（这是最后卡住的地方）：
  1. TLS 指纹要像 Chrome：Node 自带的 `fetch` 直接请求会被拦（461），改用 `curl_cffi` 的 `impersonate="chrome"`。
     **但这条只是"平时能过"**：curl_cffi 的档案并不等于本机 Chrome 153 的真实指纹。风控收紧时（例如同一账号/IP 短时间请求过多），**即使签名和请求头都完全正确，外部客户端也会被 461**，而同一时刻页面内 `fetch` 依旧 200 —— 说明拦的是连接层指纹，不是签名。
     所以 `fetch_feed.py` 内置了兜底：外部客户端三轮被拒后，自动改用**浏览器上下文**发请求。
  2. **必须带 `sec-ch-ua` / `sec-ch-ua-mobile` / `sec-ch-ua-platform` 这组 Client Hints**，而且 **UA 与这三个头必须和真机设备完全一致** —— 版本号、品牌顺序、是 `Not_A Brand` 还是 `Not?A_Brand`，差一个字符都可能被判定为"不自洽"。
     这个坑我踩过：本机是 **Chrome 153**，我照旧样本把 UA 和 Client Hints 写成了 **152** 那套常量，结果稳定 461（而且刷新凭证也没用，因为常量没变）。现在这几项在 `--refresh` 时从 `navigator.userAgent` / `navigator.userAgentData` 采集，存进 `creds.json` 的 `device` 字段。

  定位过程（值得记）：同一时刻、同一份凭证，**页面内 fetch 是 200，外部客户端是 461** —— 由此排除"账号风控"和"补环境/签名错误"。接着把页面内那次成功请求的**完整请求头**抓下来、用外部客户端原样重放 → 200；再逐条削减定位：去掉 `x-rap-param` 仍 200，**去掉 `sec-ch-ua*` 立刻 461**，最小集合测试同样 461。结论就此锁定，补上这三个头后外部客户端稳定 200。

## 四、检测点速查表

| 检测类别 | 具体表现 | 补法 |
|---|---|---|
| DOM 存在性 | 初始化第一步就 `document.body.removeChild(...)` | 真实 DOM 树、`<script>` 在 body、方法容错 |
| 标签枚举 | `getElementsByTagName('*')` 返回集合为空判非浏览器 | 实现子树遍历 |
| eval 劫持 | `eval("_ceh;window")` 能否看到局部变量 | 无需处理（Node 下天然正常） |
| 原生性 | `fn.toString()` 是否含 `[native code]` | Proxy 包 getter + `markNative` 白名单 |
| 描述符形态 | 全局属性是 accessor 还是数据属性 | 统一改成 accessor |
| 原型 Tag | `[object Navigator]` / `[object HTMLDocument]` / `[object Storage]` … | `Symbol.toStringTag` |
| DOM 怪癖 | `typeof document.all === 'undefined'` 但对象存在 | 原生 addon 造 `HTMLAllCollection` |
| Node 特征 | `process`、`require`、`module` | 藏 `process`、裸函数作用域执行 |
| 读写回环 | 写 cookie/localStorage 后读回校验 | 实现真实的读写回环 |
| 垃圾参数 | 拿 `undefined` / `window` 调 DOM 方法 | **所有方法容错，不抛异常** |
| 传输层（非环境） | 缺 `sec-ch-ua*` → 461；UA 与 Client Hints 不自洽（版本/品牌顺序不符）→ 461；Node 自带 fetch 的 TLS 也会被拦 | `curl_cffi impersonate="chrome"`，UA 与 Client Hints 全部从真机采集 |

## 五、排错方法论（比结论更有用）

1. **代理日志要记"值"，不只记"类型"。** `env.js` 里 get/set 都把 `target[property]` 打出来，很多判断靠的是值。
2. **必须有浏览器侧对照。** 伪造 `www.xiaohongshu.com` 源 + 只注入 `vmp.js`，就是一个干净可控的"真机基准"。任何"Node 里缺什么"的判断都应该先问：真机这里有没有？
3. **钩住能看到的每一层**：`new Function`（动态检测）、`WebAssembly.instantiate`（wasm）、`Promise.prototype.then` / `setTimeout`（异步里的异常）、`Object.defineProperty`（绕过代理挂属性）。
4. **浏览器侧打点要挑对象**：给 `window.mnsv2` 装 setter 能拿到"赋值时机 + 调用栈"，这是最有价值的一次探测（确定了赋值发生在**同步阶段**）。
5. **不要包装子对象做轨迹**：包装 `navigator`/`screen` 会被立刻检测到；包装 `window` 自身才相对安全（描述符陷阱可以原样透传）。

### 我走过的一次弯路（留个反面教材）

有段时间我得出结论"Node 比浏览器少一个内部槽位"，据此煞有介事地做 bisect——**结论是错的**：那个槽位是**异步**创建的，而我在 `require` 之后立刻同步取列表，自然取不到。教训：**观测时机要和被测行为匹配**，异步的用异步口径测。

## 六、最终结论与已知差异

### 验收结果

| 项 | 结论 |
|---|---|
| **补环境** | ✅ `window.mnsv2` 在纯 Node 下可用，服务端认可其产出 |
| **纯 Node 端到端** | ✅ `node fetch_feed_node.js` —— 补环境出签 + `xs_common.js`（离线复刻的 `xsCommon`）+ `@zionsssx/freq-js`（Rust 引擎，仿 Chrome JA3 + Akamai HTTP/2 指纹）传输。**不出 Node、不开浏览器、不用 Python** |
| **461 的归属** | ✅ 与签名无关。同一时刻、同一外部传输、同一 `X-S-Common`，只换 `X-s`：**页面签名 → 200、Node 签名 → 200**；反过来"页面签名 + 外部传输"在风控收紧时同样 461。⇒ 461 是**连接层指纹**问题，不是 vmp 走错分支；换成能仿 Chrome 指纹的传输即解决 |
| **X-S-Common** | ✅ **已离线化**：`xs_common.js` 复刻了 `xsCommon`，其中 `x9` 的 hash（线上 `ed.tb`）是"标准 CRC32 表 + 收尾异或 `0xEDB88320`"的变体，已用浏览器实测样本逐值校验（`'abc'` / `'123456789'` / `'xhs-pc-web'` / `''` 全部一致） |
| **剩余浏览器依赖** | 只有**一次性**采集设备原值（cookies + `a1`/`dsllt`/`b1`/`_dsl`/平台 + UA/Client Hints）写进 `creds.json`；每个请求的 `X-s`、`X-S-Common` 都由 Node 现算 |

### 已知差异（不影响取数，留作记录）

| 项 | 现象 | 说明 |
|---|---|---|
| payload 长度 | 同一入参下 Node 比浏览器短一截（如 412 vs 318） | 该长度由**虚拟机初始化那一刻的快照**决定：初始化后再拆环境（清 localStorage、关 WebGL、清 plugins、置空 Error.stack、去 performance…）长度**一律不变**；而在 Node 侧初始化前补能力（navigator 能力 / DOM 规模 / canvas / 页面级全局）长度也**一律不变**。⇒ 缺的不是"能力"，但**服务端照样接受**，不影响取数 |
| `mnsv2` 前缀 | 短入参 `mns0101_`、长入参 `mns0301_` | 由**入参**决定，不是环境差异（一开始我误判成环境变体标记） |
| wasm | 那个 36414 字节的 wasm 与 `mnsv2` 无关 | 浏览器侧和 Node 侧调用 `mnsv2` 前后，wasm 共享内存都是 **0 字节变化** |
| 传输层 | 普通 HTTP 客户端（Node 自带 `fetch` / python `requests` / `curl_cffi`）在风控收紧时会 461 | ✅ 已解决：`fetch_feed_node.js` 用 `@zionsssx/freq-js`（Rust 引擎，仿 Chrome **JA3 + Akamai HTTP/2** 指纹），纯 Node 稳定 200 |
| `X-S-Common` | 必须原样使用；采样要在站内签名请求发出之后 | 改字段、或抢在预热前采集，都会 461 |

### 可选后续（都不影响当前可用性）

1. 逆出 `xsCommon` 里 `x9` 的 hash 与 `x12` 两个时间戳语义，让凭证也能完全离线生成；
2. 查清 payload 少的那一截具体是什么（需要在浏览器**初始化前**做削减，或改喂 vmp.js + 双向轨迹 diff）；
3. 对齐本机 Chrome 的 TLS/HTTP2 指纹，让 `--direct` 稳定可用。
